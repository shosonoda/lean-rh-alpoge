This page records our own run of that procedure on RIKYU (RIKEN R-CCS), with the deviations listed below. It is not the verification carried out by the community, and it is not a statement by the community; for those, see the repository and the statement linked at the top of the Overview. The procedure of the community repositoryコミュニティのリポジトリの手順

The README of the repository describes four steps. In short:

リポジトリの README は 4 つの段階を示している．要約すると次のとおりである：

  1. Challenge export. In a clean tree that contains only Challenge.lean (a file that imports Mathlib only and restates the four definitions and the five theorems with sorry), with Lean 4.33.1: lake exe mathlib/cache get, lake build Challenge, then lake env lean4export Challenge -- $(cat export-targets.txt) > challenge.export.チャレンジのエクスポート．Challenge.lean（Mathlib だけを import し，4 つの定義と 5 つの定理を sorry で述べ直したファイル）だけを含むクリーンなツリーで，Lean 4.33.1 により lake exe mathlib/cache get，lake build Challenge，lake env lean4export Challenge -- $(cat export-targets.txt) > challenge.export を実行する．
  2. Build of the solution. Build Main of the project (in a second clone, inside a sandbox without network access).解答のビルド．プロジェクトの Main をビルドする（別の clone で，ネットワークを遮断したサンドボックスの中で）．
  3. Solution export. lake env lean4export Main -- $(cat export-targets.txt) > solution.export.解答のエクスポート．lake env lean4export Main -- $(cat export-targets.txt) > solution.export．

With Lean v4.36.0, from an empty directory: lake comparator --config comparator.json --challenge-from-export challenge.export --solution-from-export solution.export.判定．Lean v4.36.0 を使い，空のディレクトリから lake comparator --config comparator.json --challenge-from-export challenge.export --solution-from-export solution.export を実行する．

Deviations from the procedure of the communityコミュニティの手順との相違点

Our run differs from the published procedure in the following points.

我々の実行は，公表されている手順と次の点で異なる．

  1. The checker “Lean paranoid” is not run. The program leanchecker-paranoid of the Lean 4.36.0 release for aarch64 aborts at start-up on these nodes, also when it is called with --version only (message “INTERNAL PANIC: integer overflow in runtime computation”, exit code 134; the nodes use a page size of 64 KiB), so the failure does not depend on the input. lake comparator counts a checker that cannot start as a rejection. The job therefore tests whether the program starts and, if it does not, removes exactly this entry from the configuration and records that it did. The result of our run can therefore be at most “accepted by nanoda and by the Lean default kernel”; it is not a result for the complete configuration of the community.検査器「Lean paranoid」は実行していない．aarch64 用の Lean 4.36.0 リリースに含まれる leanchecker-paranoid は，このノードでは起動時に異常終了する．--version だけを指定しても同じである（メッセージは「INTERNAL PANIC: integer overflow in runtime computation」，終了コード 134．ノードのページサイズは 64 KiB）．したがってこの失敗は入力によらない．lake comparator は，起動できない検査器を拒否として数える．そこでジョブは，このプログラムが起動するかを調べ，起動しない場合に限り，設定からこの項目だけを取り除き，そのことを記録している．このため我々の実行の結果は，最良でも「nanoda と Lean の既定のカーネルによる受理」であり，コミュニティの設定全体に対する結果ではない．
  2. The solution was not built by this job inside a sandbox without network access. Its .olean files are those of our build of step 1 (the tree as distributed, which is the first commit, 40e56bab, of the community repository). That the export made from them is the same as the one of the community is established by its size and its SHA-256 only.解答は，このジョブがネットワークを遮断したサンドボックスの中でビルドしたものではない．.olean ファイルは工程 1 の我々のビルドのものである（配布時のままのツリー．これはコミュニティのリポジトリの最初の commit 40e56bab にあたる）．そこから作ったエクスポートがコミュニティのものと同じであることは，サイズと SHA-256 だけで確かめている．
  3. The sandbox program is bubblewrap 0.9.0, taken from the Ubuntu package and unpacked into the job's directory, because the nodes have no bubblewrap installed.サンドボックスのプログラムは bubblewrap 0.9.0 で，Ubuntu のパッケージから取り出してジョブのディレクトリに展開したものである（ノードには bubblewrap が導入されていない）．
  4. Hardware and operating system: aarch64 (Arm Neoverse-V2), Ubuntu 24.04, Linux with 64 KiB pages.ハードウェアと OS：aarch64（Arm Neoverse-V2），Ubuntu 24.04，ページサイズ 64 KiB の Linux．
  5. The challenge export was made in an earlier job (the third environment check) and reused; the run checks its SHA-256 again before the judge starts.チャレンジのエクスポートは，先行するジョブ（3 回目の環境の確認）で作ったものを再利用した．実行の中で，判定の開始前に SHA-256 を改めて確かめている．

Relation to step 2工程 2 との関係

Step 2 (section 3) and this page are two different checks of the same project. Step 2 uses the standalone Comparator (tag v4.33.0) with the landrun sandbox and a challenge file that we wrote, which imports the project's Statements module; Comparator rebuilds the project inside the sandbox, exports it and replays the export itself. The procedure of the community uses a challenge file that imports Mathlib only, the command lake comparator of Lean v4.36.0, which works from two export files, and the checkers named in its configuration.

工程 2（第 3 節）とこのページは，同じプロジェクトに対する 2 つの別々の検査である．工程 2 は，単体の Comparator（タグ v4.33.0）を landrun サンドボックスとともに使い，チャレンジファイルは我々が書いたもので，プロジェクトの Statements モジュールを import する．Comparator はサンドボックスの中でプロジェクトをビルドし直し，エクスポートし，そのエクスポートを自身で再生する．コミュニティの手順は，Mathlib だけを import するチャレンジファイルと，2 つのエクスポートファイルから動作する Lean v4.36.0 のコマンド lake comparator，およびその設定で指定された検査器を使う．
