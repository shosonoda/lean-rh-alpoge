What this page is, and what it is notこのページが何であり，何でないか

The repository lsernau/grh-lean is another project by other authors. Its README describes it as a shorter rewriting of the Lean proof distributed at alpo.ge, proving the same five theorems, in two editions that are separate Lake projects. We built both editions from scratch on RIKYU (RIKEN R-CCS), and ran the Comparator set-up that the repository ships.

リポジトリ lsernau/grh-lean は，別の作者による別のプロジェクトである．その README は，alpo.ge で配布されている Lean の証明を短く書き直したもので，同じ 5 つの定理を証明すると説明している．2 つの版があり，それぞれ独立した Lake プロジェクトである．我々は両方の版を RIKYU (RIKEN R-CCS) で最初からビルドした．リポジトリに含まれている Comparator の設定を実行した．

The page records what we ran and what came out. It is not the authors' own check and not a statement by them, and, as everywhere in this report, it does not assess the mathematics. The records of the distributed tree on the other pages are unchanged.

Buildビルド

Each edition was built in a job of its own, from an empty build directory on the local disk of the node, with the steps of the README: lake exe cache get, which fetches the compiled files of Mathlib (Mathlib was not compiled; the job stops if the cache is incomplete), then lake build, then lake env lean scripts/PrintAxioms.lean. The compute node fetched the commit from GitHub. LEAN_NUM_THREADS was the number of allocated cores.

各版を，それぞれ別のジョブで，ノードのローカルディスク上の空のビルドディレクトリからビルドした．手順は README のとおりで，lake exe cache get（Mathlib のコンパイル済みファイルを取得する．Mathlib はコンパイルしていない．キャッシュが不完全ならジョブを止める），lake build，lake env lean scripts/PrintAxioms.lean の順である．コミットは計算ノードが GitHub から取得した．LEAN_NUM_THREADS は割り当てたコア数にした．

ComparatorComparator

Each edition ships a Comparator set-up: Challenge.lean, which states the five theorems with sorry in place of the proofs and imports only src/Statements.lean, and comparator.json, which names the challenge module Challenge, the solution module Main, the five theorems, the permitted axioms propext, Classical.choice, Quot.sound, and asks for the additional kernel nanoda. The README names Comparator v4.35.0, the release for the Lean version of the project. Comparator builds both modules inside a sandbox, exports the theorems and everything they depend on, compares the statements, checks the axioms, and replays the proofs in the kernels.

Points in which the run differs from the instructions of Comparator, or that a reader should know:

Comparator の手順と異なる点，および読む際に知っておくべき点：

  • The guard against Unix sockets. The README of Comparator runs it under systemd-run --user with RestrictAddressFamilies=~AF_UNIX. A batch job has no systemd user session, so we used a small wrapper that installs the equivalent seccomp filter.Unix ソケットの遮断．Comparator の README は，RestrictAddressFamilies=~AF_UNIX を付けた systemd-run --user の下で実行する．バッチジョブには systemd のユーザーセッションがないので，同等の seccomp フィルタを設定する小さなラッパーを用いた．
  • The sandbox. landrun (Landlock), built from its main branch, as the README of Comparator asks.サンドボックス．Comparator の README のとおり，main ブランチからビルドした landrun（Landlock）を用いた．
  • The nanoda binary. The README of Comparator builds nanoda from source. We used the nanoda_bin of the Lean toolchain of the project, after it gave the right answers on three small test projects (one to accept, two to reject).nanoda のバイナリ．Comparator の README は nanoda をソースからビルドする．我々は，プロジェクトの Lean の toolchain に含まれる nanoda_bin を，3 つの小さなテスト用プロジェクト（受理すべきもの 1 つ，拒否すべきもの 2 つ）で正しい答えを出すことを確かめたうえで用いた．
  • Stack. The stack limit was raised (ulimit -s unlimited), as the README of the repository does for its own run.スタック．リポジトリの README が自身の実行で行っているのと同じく，スタックの上限を上げた（ulimit -s unlimited）．
  • The Mathlib cache is trusted. As the README of Comparator allows, the compiled files of Mathlib were fetched with lake exe cache get before the run; Mathlib was not recompiled.Mathlib のキャッシュを信頼している．Comparator の README が認めているとおり，実行の前に lake exe cache get で Mathlib のコンパイル済みファイルを取得した．Mathlib はコンパイルし直していない．
