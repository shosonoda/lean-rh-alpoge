import Mathlib

def RiemannZetaZerosOnLine : Prop :=
  ∀ s : ℂ, riemannZeta s = 0 → (¬∃ n : ℕ, s = -2 * ((n : ℂ) + 1)) → s ≠ 1 → s.re = 1 / 2

def DirichletLNonvanishingRightOfHalf : Prop :=
  ∀ (N : ℕ) [NeZero N] (χ : DirichletCharacter ℂ N) (s : ℂ),
    1 / 2 < s.re → (χ ≠ 1 ∨ s ≠ 1) → DirichletCharacter.LFunction χ s ≠ 0

def DirichletLZerosOnLine : Prop :=
  ∀ (N : ℕ) [NeZero N] (χ : DirichletCharacter ℂ N) (s : ℂ),
    0 < s.re → s.re < 1 → DirichletCharacter.LFunction χ s = 0 → s.re = 1 / 2

def PrimitiveDirichletLZerosOnLine : Prop :=

2Step 1: build工程 1：ビルド

Method方法

Step 1 is an ordinary build with Lake, the build tool of Lean, on one node of RIKYU (RIKEN R-CCS). The command was lake exe cache get && lake build -v. Lake elaborates the modules in dependency order. While a module is elaborated, each declaration is type-checked by the Lean kernel before it is added to the environment, and the result is written to an .olean file.

工程 1 は，RIKYU (RIKEN R-CCS) の 1 ノード上で，Lean のビルドツール Lake による通常のビルドである．実行したコマンドは lake exe cache get && lake build -v である．Lake は依存関係の順にモジュールをエラボレートする．モジュールのエラボレート中，各宣言は環境に追加される前に Lean カーネルによって型検査され，結果は .olean ファイルに書き出される．

lake exe cache get downloads the prebuilt .olean files of Mathlib, so Mathlib itself was not rebuilt in this step.

lake exe cache get は Mathlib のビルド済み .olean ファイルをダウンロードする．したがってこの工程では Mathlib 自体は再ビルドしていない．

A build that finishes without errors shows that Lean accepted every module. It is a weaker check than step 2, because the project's own build configuration and metaprograms run during the build. The statistics below are computed from the verbose build logs by analysis/build_log_stats.py.

エラーなしで完了したビルドは，Lean がすべてのモジュールを受理したことを示す．ただしビルド中にはプロジェクト自身のビルド設定やメタプログラムが実行されるため，工程 2 より弱い検査である．以下の統計は，詳細ビルドログから analysis/build_log_stats.py により計算した．

Notes

注記

  • The build was done in three Slurm jobs. Each job saved .lake/build to shared storage when it stopped and the next job restored it, so Lake replayed the modules already built instead of compiling them again. The columns “modules at start” and “modules at end” count the .olean files of the project before and after each job.ビルドは 3 つの Slurm ジョブに分けて行った．各ジョブは停止時に .lake/build を共有ストレージに保存し，次のジョブがそれを復元したので，Lake はビルド済みのモジュールをコンパイルし直さずに再生した．表の「開始時」「終了時」のモジュール数は，各ジョブの前後でのプロジェクトの .olean ファイル数である．
  • Lake writes one *.setup.json file per module (the artifact paths of all transitive imports, 5 MB or more each). These files were deleted while the build was running and were not saved; Lake does not need them to replay a module. In the first job, which kept them, they took 30.1 GB for 3,558 modules, against 4.1 GB of .olean files.Lake はモジュールごとに *.setup.json（推移的な import すべての成果物パス．1 個 5 MB 以上）を書く．これらはビルド中に削除し，保存していない（Lake がモジュールを再生するのに必要ない）．削除しなかった最初のジョブでは，3,558 モジュールで 30.1 GB を占めていた（.olean は 4.1 GB）．

What Comparator checksComparator が検査すること

Comparator is a tool from the Lean FRO for judging whether a Lean project proves a given list of theorems. It is given a challenge module that states the theorems, a solution module that is claimed to prove them, the names of the theorems, and the list of axioms that may be used. As described in its documentation, it then:

Comparator は，ある Lean プロジェクトが与えられた定理の一覧を証明しているかを判定するための，Lean FRO のツールである．定理を述べたチャレンジモジュール，それらを証明していると主張される解答モジュール，定理の名前，使用を許可する公理の一覧を入力とする．ドキュメントによれば，Comparator は次のことを行う：

  • rebuilds the solution inside a sandbox, so that code of the project that runs during the build cannot reach the checker or its inputs;サンドボックスの中で解答を再ビルドする．これにより，ビルド中に実行されるプロジェクトのコードが，検査器やその入力に触れることはできない．
  • exports the challenge and the solution with lean4export and compares them: each listed theorem must have the same statement in both, including the definitions that the statement depends on;lean4export によりチャレンジと解答をエクスポートして比較する．列挙された各定理は，言明が依存する定義まで含めて，両者で同じ言明を持たなければならない．
  • collects the axioms that the listed theorems of the solution depend on and rejects if one of them is not on the permitted list;解答中の列挙された定理が依存する公理を集め，許可された一覧にないものがあれば拒否する．
  • replays the exported solution in the Lean kernel, so that the proofs are checked again from the exported data.エクスポートした解答を Lean カーネルで再生し，エクスポートされたデータから証明を改めて検査する．

Limitations and remarks制約と補足

  • Comparator (github.com/leanprover/comparator, tag v4.33.0) and lean4export were compiled with the project's toolchain, Lean 4.33.1; the tag itself pins Lean 4.33.0.Comparator（github.com/leanprover/comparator，タグ v4.33.0）と lean4export は，プロジェクトの toolchain である Lean 4.33.1 でコンパイルした（タグ自体が指定しているのは Lean 4.33.0 である）．
  • The Comparator README recommends starting it under systemd-run with RestrictAddressFamilies=~AF_UNIX, to guard against a weakness of the landrun sandbox on Linux kernels before 7.1. systemd-run --user is not available inside a batch job on this machine (kernel 7.0), so Comparator was started under a small seccomp wrapper that makes socket(AF_UNIX, ...) fail instead. A test in the job confirms that the wrapper blocks the call.Comparator の README は，Linux カーネル 7.1 より前で landrun サンドボックスにある弱点への対策として，systemd-run に RestrictAddressFamilies=~AF_UNIX を付けて起動することを勧めている．この計算機（カーネル 7.0）のバッチジョブ内では systemd-run --user が使えないため，socket(AF_UNIX, ...) を失敗させる小さな seccomp ラッパーの下で Comparator を起動した．ラッパーがこの呼び出しを遮断することは，ジョブ内のテストで確認している．
  • Comparator builds the solution inside the sandbox with all hardware threads of the node. The sandboxed build does not fit in one job, so .lake/build of the sandbox is saved when a job stops and restored by the next one, as in step 1. Lake then decides from its trace files which modules are up to date; the modules compiled in an earlier job are not compiled again.Comparator は，サンドボックス内でノードの全ハードウェアスレッドを使って解答をビルドする．このビルドは 1 つのジョブに収まらないので，ステップ 1 と同じく，ジョブの停止時にサンドボックスの .lake/build を保存し，次のジョブで復元している．どのモジュールが最新かは Lake が trace ファイルから判断し，前のジョブでコンパイルされたモジュールはコンパイルし直されない．
  • Size of the export, measured separately on the build of step 1: lean4export, called with the same list of declarations as Comparator uses, wrote 61.6 GB (61,571,290,930 bytes, 1,080,769,500 lines) for the solution in 1 h 26 min, with a peak memory of 170 GB. Comparator keeps this export in memory, parses it, and replays it in the Lean kernel in a single thread.エクスポートの大きさ（ステップ 1 のビルドに対して別途測定）: Comparator と同じ宣言の一覧を与えた lean4export は，解答について 61.6 GB（61,571,290,930 バイト，1,080,769,500 行）を 1 時間 26 分で出力し，最大メモリ使用量は 170 GB だった．Comparator はこのエクスポートをメモリ上に保持して解析し，Lean のカーネルで単一スレッドで再生する．
  • Kernel time, estimated separately: a uniform random sample of 960 modules was elaborated again with Lean's profiler. The mean time spent in kernel type checking was 0.40 s per module (standard error 0.08 s), which scales to about 19 hours (standard error 4 hours) for the 175,187 modules. The replay covers the cone of the five theorems (66% of the project constants) and the part of Mathlib that they depend on, so this figure indicates the order of magnitude only.カーネルの時間（別途の見積もり）: 無作為に選んだ 960 モジュールを Lean の profiler つきで処理し直した．カーネルの型検査にかかった時間の平均は 1 モジュールあたり 0.40 秒（標準誤差 0.08 秒）で，175,187 モジュールに換算すると約 19 時間（標準誤差 4 時間）になる．再生の対象は 5 つの定理のコーン（プロジェクトの定数の 66%）と，それらが依存する Mathlib の部分なので，この数値は桁の目安にとどまる．
