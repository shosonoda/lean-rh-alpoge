How the builds were runビルドの方法

  • Sources. The compute node fetched commit 9282d3a1 from GitHub. It has 59,869 .lean files under src/.ソース．計算ノードが GitHub からコミット 9282d3a1 を取得した．src/ の .lean ファイルは 59,869 個である．
  • Steps. Lean v4.37.0-rc1 was installed, the compiled files of Mathlib were fetched from its cache (lake exe mathlib/cache get; Mathlib was not compiled), and lake build -v was run with LAKE_ARTIFACT_CACHE=false. No compiled file of the project was fetched: every module of the project was compiled in the job.手順．Lean v4.37.0-rc1 を入れ，Mathlib のコンパイル済みファイルをそのキャッシュから取得し（lake exe mathlib/cache get．Mathlib はコンパイルしていない），LAKE_ARTIFACT_CACHE=false を設定して lake build -v を実行した．プロジェクトのコンパイル済みファイルは取得していない．プロジェクトのモジュールは，すべてジョブの中でコンパイルした．
  • Place. The build directory was on the local NVMe disk of the node and was empty at the start; nothing was saved or resumed.場所．ビルドのディレクトリはノードのローカル NVMe ディスクに置き，開始時は空だった．途中の保存や再開はしていない．
  • Threads. LEAN_NUM_THREADS, the number of modules Lake compiles at the same time, was set to the number of allocated cores (1 GPU = 32 cores, 2 GPU = 64 cores, 4 GPU = 144 cores). The three jobs ran on different nodes at overlapping times; each thread count was run once.スレッド数．Lake が同時にコンパイルするモジュールの数 LEAN_NUM_THREADS を，割り当てたコア数にした（1 GPU = 32 コア，2 GPU = 64 コア，4 GPU = 144 コア）．3 つのジョブは別々のノードで，重なる時間帯に実行した．どのスレッド数も 1 回だけ実行した．
  • Measurement. The time is the wall-clock time of lake build, from its start to its end. Every 15 seconds the job recorded the number of .olean files written, the number of lean processes, and the CPU time used by the job (from its control group).計測．時間は lake build の開始から終了までの実時間である．ジョブは 15 秒ごとに，できた .olean ファイルの数，lean プロセスの数，ジョブが使った CPU 時間（コントロールグループの値）を記録した．
  • Machine. RIKYU (RIKEN R-CCS): one compute node with 144 cores (Neoverse-V2, aarch64). Lake version 5.0.0-src+0b77e12 (Lean version 4.37.0-rc1).計算機．RIKYU (RIKEN R-CCS) の計算ノード 1 台（144 コア，Neoverse-V2，aarch64）．Lake version 5.0.0-src+0b77e12 (Lean version 4.37.0-rc1)．

Threads and speedスレッド数と速さ

  • 32 → 64 threads: 1.48 times faster for 2 times the cores (1.48 per doubling).32 → 64 スレッド：コア数 2 倍に対して 1.48 倍（2 倍あたり 1.48 倍）．
  • 64 → 144 threads: 1.74 times faster for 2.25 times the cores (1.60 per doubling).64 → 144 スレッド：コア数 2.25 倍に対して 1.74 倍（2 倍あたり 1.60 倍）．
  • 32 → 144 threads: 2.58 times faster for 4.50 times the cores (1.55 per doubling).32 → 144 スレッド：コア数 4.50 倍に対して 2.58 倍（2 倍あたり 1.55 倍）．

The shortfall from proportionality has two parts.

比例から外れる分は，2 つに分けられる．

  • The same build takes more CPU time. The CPU time of the job was 78.7 core-hours at 32 threads, 102.8 core-hours at 64 threads, 117.8 core-hours at 144 threads. At 144 threads the build did 1.5 times the computation of the build at 32 threads. In all three builds the load of the node (threads waiting to run) was two to two and a half times the number of allocated cores: a lean process uses several threads, and they compete for the cores. Competition for memory bandwidth is another possible cause. We did not separate the two.同じビルドに使う CPU 時間が増える．ジョブの CPU 時間は，32 スレッドで 78.7 コア時間，64 スレッドで 102.8 コア時間，144 スレッドで 117.8 コア時間だった．144 スレッドのビルドは，32 スレッドのビルドの 1.5 倍の計算をしている．どのビルドでも，ノードの負荷（実行待ちのスレッド数）は割り当てたコア数の 2〜2.5 倍あった．lean プロセス 1 つが複数のスレッドを使い，それらがコアを取り合っている．メモリ帯域の取り合いも原因として考えられる．この 2 つは切り分けていない．

Together: 4.50 times the cores, divided by 1.50 for the larger CPU time and multiplied by 0.86 for the lower share in use, gives 2.58, the measured ratio of 2.58.

合わせると，コア数 4.50 倍を，CPU 時間の増加の 1.50 で割り，使用率の低下の 0.86 を掛けて，2.58 倍になる．実測の比は 2.58 倍である．

On the distributed tree with Lean v4.33.1, short trials had shown the opposite at 144 threads: the build rate fell to about 176 modules per minute, below the rate at 96 threads (Build analysis, section 5). That did not happen here: at 144 threads, 59,868 modules were compiled in 57 min 49 s, about 1,036 per minute on average. The version of Lake, the number of modules and the size of the import closures all differ between the two cases; we did not isolate the cause.

配布時のツリーと Lean v4.33.1 では，短い試行で，144 スレッドにすると逆の結果が出ていた．ビルド速度は毎分 約 176 モジュールに落ち，96 スレッドのときより遅かった（ビルドの解析，第 5 節）．今回はそれが起きなかった．144 スレッドで，59,868 モジュールを 57 分 49 秒でコンパイルしており，平均で毎分 約 1,036 モジュールである．2 つの場合では，Lake の版，モジュール数，import の閉包の大きさがどれも違う．原因は切り分けていない．

What the build graph allowsビルドグラフから決まる限界

Lake compiles one module (one .lean file) per lean process, and starts a module when all the modules it imports are done. The time of a build is therefore set by three things: the total work (the sum of the module times), the longest chain of modules that import one another, and the fixed cost of each module (starting the process and loading its imports).

Lake は，モジュール（.lean ファイル）1 つを lean プロセス 1 つでコンパイルし，import するモジュールがすべてできてから，そのモジュールを始める．したがってビルドの時間は，仕事量の合計（モジュール時間の和），互いに import し合うモジュールの最長の鎖，モジュールごとの固定費（プロセスの起動と import の読み込み），の 3 つで決まる．
